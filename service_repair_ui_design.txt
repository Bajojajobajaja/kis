================================================================================
ПРОЕКТИРОВАНИЕ ИНТЕРФЕЙСА ПОДСИСТЕМЫ «СЕРВИС И РЕМОНТ»
КИС ООО «Nexus» (автодилерский центр)
================================================================================

Документ дополняет раздел курсовой работы по подсистеме «Сервис и ремонт»
четырьмя обязательными составляющими проекта пользовательского интерфейса:

  1. Карта сайта (sitemap) веб-приложения.
  2. Граф диалога (state-diagram переходов между экранами).
  3. Проект диалоговых окон (форм).
  4. Макеты выходных документов.
  5. Контрольный пример (сквозной сценарий).

ИСХОДНЫЕ ДАННЫЕ
- Веб-приложение SPA, React + Vite, маршрутизация react-router-dom.
- Корневая страница подсистемы: /service.
- Реализующие микросервисы: service-appointments, service-workorders,
  service-diagnostics, service-labor-catalog, service-parts-usage,
  service-billing (плюс интеграции с crm-contacts, masterdata-catalog,
  inventory-stock, inventory-procurement, finance-invoicing, notification).

================================================================================
1. КАРТА САЙТА (SITEMAP)
================================================================================

Карта сайта отражает иерархию маршрутов подсистемы и точки входа из общей
навигации КИС. Уровни отступа = уровни вложенности URL. В скобках указан
маршрут react-router и роль, которой доступен экран.

[Главная КИС]   /                                          (любой авторизованный)
 │
 ├── [Поиск по всем сущностям]   /search                   (все роли)
 │
 └── [Подсистема «Сервис и ремонт»]   /service             (service_advisor,
      │                                                     service_manager,
      │                                                     platform_admin)
      │
      ├── [Аналитика сервиса]         /service/analytics   (service_manager,
      │                                                     platform_admin)
      │     ├── KPI: % SLA, средний срок, % повторных визитов
      │     ├── Загрузка боксов (heat-map)
      │     └── Качество (NPS, qualityScore)
      │
      ├── [Записи на сервис]          /service/appointments
      │     ├── [Список + календарь слотов]
      │     ├── [Карточка записи]     /service/appointments/{id}
      │     │     ├── Подтверждение
      │     │     ├── Назначение мастера-приёмщика
      │     │     ├── Отмена
      │     │     └── Конвертация в заказ-наряд
      │     └── [Диалог «Новая запись»]   (модальное окно)
      │
      ├── [Заказ-наряды]              /service/orders
      │     ├── [Канбан по статусам:  accepted → diagnostics →
      │     │   in_progress ⇄ waiting_parts → ready → released → closed]
      │     ├── [Карточка заказ-наряда]   /service/orders/{id}
      │     │     ├── Вкладка «Общее» (VIN, клиент, SLA, исполнитель)
      │     │     ├── Вкладка «Диагностика» (дефекты, протокол)
      │     │     ├── Вкладка «Работы»   (labor-позиции, нормо-часы)
      │     │     ├── Вкладка «Запчасти» (резерв/расход/возврат)
      │     │     ├── Вкладка «Биллинг» (счета, оплаты, акты)
      │     │     ├── Вкладка «Качество» (оценка, повторный визит)
      │     │     └── Вкладка «История событий» (event-log)
      │     └── [Диалог «Новый заказ-наряд»]
      │
      ├── [Сервисные документы]       /service/documents
      │     ├── Счета (ServiceInvoice)
      │     ├── Акты выполненных работ
      │     └── Гарантийные талоны
      │
      └── [События подсистемы]        /service/events
            ├── BookingCreated, WorkOrderOpened,
            ├── DiagnosticsCompleted, PartsReserved,
            ├── PartsDeficitDetected, WorkOrderCompleted,
            ├── VehicleReleased, ServicePaid
            └── (read-only журнал)

Внешние ссылки (cross-subsystem, открываются в подсистемах-владельцах):
  • Контакт клиента      → /crm/contacts/{client_id}    (crm-contacts)
  • Карточка автомобиля  → /masterdata/vehicles/{vin}   (masterdata-catalog)
  • Резерв на складе     → /inventory/stock/{sku}        (inventory-stock)
  • Счёт-фактура         → /finance/invoices/{id}        (finance-invoicing)

-----------------------------------

   ┌──────────────────┐  логин   ┌────────────────────┐
   │ /login           ├─────────►│  Главная /         │
   └──────────────────┘          └─────────┬──────────┘
                                           │ выбор «Сервис и ремонт»
                                           ▼
                                 ┌────────────────────┐
                                 │ /service           │
                                 │ (редирект на одну  │
                                 │  из вкладок)       │
                                 └─────────┬──────────┘
                  ┌────────────────────────┼────────────────────────┐
                  ▼                        ▼                        ▼
        ┌────────────────┐     ┌────────────────────┐     ┌──────────────────┐
        │ /appointments  │     │ /orders            │     │ /documents       │
        │ (записи)       │     │ (заказ-наряды)     │     │ (счета/акты)     │
        └───────┬────────┘     └─────────┬──────────┘     └────────┬─────────┘
                │ выбор записи           │ выбор карточки          │ выбор док-та
                ▼                        ▼                         ▼
        ┌────────────────┐     ┌────────────────────┐     ┌──────────────────┐
        │ /appointments/ │     │ /orders/{id}       │     │ /documents/{id}  │
        │   {id}         │◄────┤  (вкладки)         │────►│  (печать, PDF)   │
        └────────┬───────┘     └──┬─────────┬───────┘     └──────────────────┘
                 │                │         │
                 │ «Открыть WO»   │ переход │ переход
                 ▼                ▼         ▼
            (создаётся WO)   /search   /service/events
                                       (event log)

Кнопка «Назад» браузера = react-router useNavigate(-1).
Каждый модальный диалог наслаивается над текущим экраном и не меняет URL.

2.2. Граф состояний заказ-наряда (WorkOrder)
---------------------------------------------

  [START]
     │ создание записи и приёмки авто
     ▼
  ┌──────────┐   назначение     ┌────────────┐  завершение     ┌──────────────┐
  │ accepted ├─────────────────►│ diagnostics├────────────────►│ in_progress  │
  │ (принят) │   диагноста      │(диагностика)│ протокола       │ (в работе)   │
  └──────────┘                  └────────────┘                 └──────┬───────┘
                                                                      │ нет запчастей
                                                                      ▼
                                                              ┌────────────────┐
                                                              │ waiting_parts  │
                                                              │(ожидание з/ч)  │
                                                              └──────┬─────────┘
                                                                     │ запчасти есть
                                                                     ▼
                                                              ┌──────────────┐
                                                              │ in_progress  │
                                                              └──────┬───────┘
                                                                     │ все работы выполнены,
                                                                     │ контроль качества пройден
                                                                     ▼
                                                              ┌──────────────┐
                                                              │   ready      │
                                                              │  (готов)     │
                                                              └──────┬───────┘
                                                                     │ мастер-приёмщик
                                                                     │ выдаёт авто
                                                                     ▼
                                                              ┌──────────────┐
                                                              │  released    │
                                                              │  (выдан)     │
                                                              └──────┬───────┘
                                                                     │ событие ServicePaid
                                                                     │ из finance-invoicing
                                                                     ▼
                                                              ┌──────────────┐
                                                              │   closed     │ ←─ [END]
                                                              │  (закрыт)    │
                                                              └──────────────┘

  Дополнительные переходы:
    • Любой статус ─ «отмена» ─►  cancelled (компенсационная saga)
    • ready ─ «возврат на доработку» ─►  in_progress
    • closed ─ «гарантийный возврат» ─►  новый WO с repeat_visit = true,
                                          previous_workorder_id = старый WO

3. ПРОЕКТ ДИАЛОГОВЫХ ОКОН (ФОРМ)
================================================================================

Используется консистентный layout (см. компонент CrmWorkbench в коде):
header (заголовок + действия) → body (поля формы / таблицы) → footer (кнопки).
Все формы — модальные диалоги, открываются поверх рабочего стола (workbench).

Условные обозначения:
  [   ]   текстовое поле       [ v]   выпадающий список
  [_x_]   обязательное поле    [ ]    чекбокс
  (...)   подсказка/placeholder  [Btn] кнопка

5. КОНТРОЛЬНЫЙ ПРИМЕР (СКВОЗНОЙ СЦЕНАРИЙ)
================================================================================

Цель: продемонстрировать корректность работы подсистемы на типовом сценарии
«запись → диагностика → ремонт с дефицитом запчастей → выдача → оплата».

ИСХОДНЫЕ ДАННЫЕ
  Клиент:         Иванов Иван Иванович (client_id = c-1057, тел. +7-915-000-00-00)
  Автомобиль:     Toyota Camry, VIN XW7BF4FK30S123456, пробег 47 320 км
  Жалоба:         стук в передней подвеске от 40 км/ч
  Запас на скл.:  PART-STAB-LH = 1 шт (нужно 2), PART-PAD-FR = 1 к-т, OK
  SLA:            48 ч
  Дата:           05.06.2026, 10:30

------------------------------------------------------------------------
Шаг 1. Запись на сервис (роль: service_advisor — Петров)
------------------------------------------------------------------------
  Действие: открыть /service/appointments → «+ Создать»
  Ввод:     клиент, VIN, причина, слот A1@10:30 05.06.2026, SLA = 48 ч.
  Ожидаемый результат:
     • создана запись AP-20148 со статусом planned;
     • слот A1@10:30 → reserved (reserved_count++);
     • опубликовано событие BookingCreated;
     • клиенту отправлено SMS-подтверждение (notification).

------------------------------------------------------------------------
Шаг 2. Приёмка автомобиля (роль: service_advisor)
------------------------------------------------------------------------
  Действие: открыть AP-20148 → «Открыть заказ-наряд».
  Ожидаемый результат:
     • создан WO-10035, status = accepted, vehicle_vin, owner_id = Петров;
     • sla_deadline = 07.06.2026 10:30 (UTC), sla_hours = 48;
     • опубликовано событие WorkOrderOpened;
     • запись AP-20148 → confirmed.

------------------------------------------------------------------------
Шаг 3. Назначение диагноста (роль: service_manager)
------------------------------------------------------------------------
  Действие: в карточке WO-10035 кнопка «Назначить исполнителя» → Сидоров.
  Ожидаемый результат:
     • WO-10035.assignee = «Сидоров С. С.»;
     • status = diagnostics.

------------------------------------------------------------------------
Шаг 4. Заполнение протокола диагностики (роль: service_advisor — Сидоров)
------------------------------------------------------------------------
  Действие: вкладка «Диагностика» → форма Ф3 (см. выше).
       Дефекты: износ стоек стабилизатора (средняя), колодки <2 мм (высокая).
       Рекомендованы: LBR-SUS-STB (1,5 н/ч), LBR-BRK-PAD (0,8 н/ч),
                      PART-STAB-LH ×2, PART-PAD-FR ×1.
  Ожидаемый результат:
     • сохранён протокол; рассчитан предв. итог 8 385 ₽;
     • опубликовано DiagnosticsCompleted;
     • статус WO-10035 → in_progress;
     • клиенту в личный кабинет отправлено уведомление о согласовании.

------------------------------------------------------------------------
Шаг 5. Резервирование запчастей — обнаружен дефицит
------------------------------------------------------------------------
  Действие: вкладка «Запчасти» → форма Ф4. Резерв PART-STAB-LH ×2.
  Состояние склада: available = 1, нужно 2 → дефицит 1 шт.
  Ожидаемый результат:
     • PartsReserved (1 шт зарезервирована);
     • PartsDeficitDetected (1 шт в дефиците);
     • в inventory-procurement автоматически создана закупка PO-9078
       у поставщика «АвтоПартс» на 1 шт, eta 07.06.2026 12:00;
     • WO-10035 → waiting_parts; sla_breached = false (укладываемся).

------------------------------------------------------------------------
Шаг 6. Поступление недостающей запчасти
------------------------------------------------------------------------
  Действие: на следующий день кладовщик принимает PO-9078.
  Ожидаемый результат:
     • inventory-stock: PART-STAB-LH available += 1 → 2 шт зарезерв. под WO;
     • WO-10035 автоматически возвращается в in_progress (событие
       PartsAvailable из inventory-stock).

------------------------------------------------------------------------
Шаг 7. Выполнение работ и списание запчастей
------------------------------------------------------------------------
  Действие: техник выполняет работы; вкладка «Запчасти» → «Списание»
            для PART-STAB-LH ×2 и PART-PAD-FR ×1.
  Ожидаемый результат:
     • PartsConsumed × 2 события;
     • остатки склада уменьшаются, резервы снимаются;
     • вкладка «Работы»: фактические нормо-часы фиксируются.

------------------------------------------------------------------------
Шаг 8. Контроль качества и переход в ready
------------------------------------------------------------------------
  Действие: форма Ф5 «Завершение WO»; quality_score = 95, comment OK,
            галки «Сформировать счёт» и «Сформировать акт».
  Ожидаемый результат:
     • WO-10035 → ready;
     • опубликовано WorkOrderCompleted;
     • service-billing создаёт счёт SI-30412 (status = issued, 8 385 ₽);
     • service-workorders формирует акт SA-20017 (status = draft).

------------------------------------------------------------------------
Шаг 9. Выдача автомобиля (роль: service_advisor)
------------------------------------------------------------------------
  Действие: кнопка «Выдать клиенту» → диалог подписи акта.
            Клиент подписывает SA-20017 → status = posted.
  Ожидаемый результат:
     • WO-10035.released_at = текущий момент;
     • WO-10035 → released;
     • опубликовано VehicleReleased;
     • notification: клиенту отправлена ссылка на оплату.

------------------------------------------------------------------------
Шаг 10. Оплата и автоматическое закрытие WO
------------------------------------------------------------------------
  Действие: клиент оплачивает счёт SI-30412 через банк.
            finance-invoicing получает выписку, помечает счёт paid и
            публикует ServicePaid (workOrderId = WO-10035, amount = 8385).
  Ожидаемый результат:
     • service-workorders ловит ServicePaid → WO-10035 → closed;
     • опубликовано WorkOrderClosed;
     • analytics-marts фиксирует закрытый WO в витрине KPI.

ПРОВЕРКА РЕЗУЛЬТАТОВ
  □ В журнале событий /service/events видна полная цепочка:
        BookingCreated → WorkOrderOpened → DiagnosticsCompleted →
        PartsReserved → PartsDeficitDetected → PartsAvailable →
        PartsConsumed×2 → WorkOrderCompleted → VehicleReleased →
        ServicePaid → WorkOrderClosed.
  □ Витрина аналитики: средний срок учитывает 34 ч (укладываемся в 48);
    sla_breached = false; qualityScore = 95.
  □ Печатные формы (заказ-наряд, акт, счёт) генерируются корректно
    (см. макеты в разделе 4).
  □ На каждом шаге роли (service_advisor, service_manager) имеют
    доступ только к разрешённым действиям (RBAC).

НЕГАТИВНЫЕ ВЕТКИ (краткий перечень)
  • Запчасть так и не поступила к sla_deadline → sla_breached = true,
    дашборд KPI подсвечивает WO красным.
  • Клиент отказался от части работ → форма «Согласование» позволяет
    исключить позицию; пересчёт итога.
  • Повторный визит по тому же дефекту в течение 30 дней →
    repeat_visit = true, previous_workorder_id = WO-10035, работа
    выполняется по гарантии (нулевая сумма).
  • Отмена записи клиентом до приёмки → AP → cancelled, слот
    возвращается в available.

ПРИЛОЖЕНИЕ. ЧТО НЕЛЬЗЯ ОТРАЗИТЬ В TXT — И ГДЕ ЭТО ДЕЛАТЬ
================================================================================

Текстовый формат не поддерживает цвет, точное позиционирование, типографику,
бинарные ресурсы и интерактивные элементы. Ниже — что и где оформлять.

  1. Цветной и пиксельно точный макет UI, гайд по компонентам.
     → Figma. Файл «KIS / Service & Repair» с фреймами под каждый
       экран и состояние, design tokens, библиотека компонентов
       (Button, Modal, Table, Kanban-column, StatusBadge).

  2. Кликабельный прототип (демонстрация переходов).
     → Figma Prototype или Marvel. Связать фреймы по событиям onClick
       соответственно графу диалога из раздела 2.

  3. Стилизованные шаблоны печатных документов (с логотипом, шрифтами,
     цветовой схемой бренда).
     → Шаблоны .docx / .odt (Microsoft Word, LibreOffice Writer) или
       .html с CSS-печатью; для серверной генерации PDF — wkhtmltopdf,
       Puppeteer или Apache FOP с XSL-FO; шаблон XSL-FO разместить в
       services/service-billing/templates/.

  4. UML-диаграммы (use-case, sequence, activity).
     → PlantUML (текст → SVG), draw.io / diagrams.net (XML с экспортом
       в SVG/PNG), Mermaid (включается прямо в Markdown).
     Файлы хранить в docs/diagrams/service/, скомпилированные
     изображения — в docs/diagrams/service/build/.

  5. ER-диаграмма данных (рис. 3 курсовой).
     → dbdiagram.io (DSL), draw.io или PlantUML er-diagrams.

  6. Реальные скриншоты работающего интерфейса (для глав «Результаты»
     и «Контрольный пример»).
     → Скриншот-инструмент Windows (Shift+Win+S), сохранять как PNG
       в docs/images/service/. Источник: запущенный SPA на
       http://localhost:5173/service после `docker compose up` и
       `npm run dev`.

  7. Видеодемонстрация сквозного сценария (раздел 5).
     → Запись экрана (OBS Studio, Xbox Game Bar Win+G);
       видеофайл .mp4 — приложение к курсовой на электронном носителе.

  8. Презентация для защиты (слайды).
     → PowerPoint / Keynote / Google Slides.

  9. Точная карта компонентов React по реальному коду
     (props, state, контексты).
     → IDE-навигация в WebStorm / VS Code; для документации
       сгенерировать с помощью react-docgen или Storybook
       (frontend/web/.storybook/).

 10. Интерактивные графики и дашборды KPI сервиса.
     → Grafana, дашборд «Service & Repair KPI» на основе данных из
       analytics-marts; URL в инфраструктуре: http://localhost:3000
       (профиль observability docker-compose).
